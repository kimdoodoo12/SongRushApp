# 163 · Sending a chat line no longer shrinks the mobile web for good

Owner (phone, Chrome 157): typing in the choice room's chat panel right after a reveal left the screen stuck (input at the top, lower half empty, nothing responding).
- Cause (implementer, from the Flutter 3.50 sources): the web engine keeps the view's size on a browser resize while text editing is on and takes the visual viewport's height while it is off (`flutter_web_sdk/lib/ui/src/engine/window.dart:352-366`); on the web a pointer-down outside a TextField unfocuses it (`editable_text.dart:6947-6951`); our 보내기 button sat outside the field and `_send` refocused it on pointer-up. In that gap the keyboard animated, the engine sized the view to the keyboard-open height, editing came back on and the view kept that height when the keyboard closed. The layout itself was correct in every state.
- Fix: 보내기 is inside the field's `TextFieldTapRegion` (`mobile/lib/ui/chat_panel.dart`), so sending never drops the text connection. Guard (`mobile/lib/platform/stale_view_guard.dart`, started from `keyboard_inset_web.dart`): if the keyboard has been down 300 ms but the view is shorter than the window, unfocus and make the engine re-measure (a `resize` on `visualViewport`), at most once a second.
- Evidence: `panel_keyboard_test.dart` (9 tests, simulating the engine rule): the owner's sequence failed before the fix with the view at 544 px instead of 844 and passes after; every game state with the panel open lays out; the guard restores 844 and fails without its unfocus. Lead: app tests +169 in a fresh copy, `flutter analyze` no issues; implementer web build OK.
- Not verified on a real phone yet; with `?debug=1` the flutter-view height should match `inner` after sending and hiding the keyboard.
