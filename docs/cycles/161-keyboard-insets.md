# 161 · The mobile web follows the real keyboard

Owner on a phone (Chrome 157): after typing in the choice room's chat panel the screen stayed squeezed, the second top line gone, the lower half empty, nothing responding. Lead's reproduction on the Android emulator (Chrome 136, host GPU) against the live site: with the keyboard up `innerHeight` and the flutter-view stay 810 while `visualViewport.height` drops to 498; after Android back the layout stays at the keyboard-open size (`docs` screenshots in the job folder, not committed). The nickname dialog's OK button also sat under the keyboard. A viewport meta `interactive-widget=resizes-content` was tried and Flutter rewrote it.
(The emulator's default software GPU also showed CanvasKit shader compile errors and a blank screen; with the host GPU it rendered; treated as an emulator artefact.)

Fix: on the web the app reads the keyboard height from the browser (`innerHeight - visualViewport.height - visualViewport.offsetTop`, on visualViewport resize/scroll, window resize and focus changes, re-read after a frame and 400 ms) and overrides MediaQuery's viewInsets for the whole app (`mobile/lib/platform/keyboard_inset*.dart`, `app.dart`); the page is scrolled back to the top when no keyboard shows; the nickname dialog pads itself above the keyboard.
Evidence: implementer `flutter analyze` no issues; app tests +160 (new: the inset maths, the stub, the app following an injected inset over Flutter's own, a choice room with the chat panel going 300 → 0 restoring the second line and the panel size with focus kept, the dialog's OK above a 400 px keyboard); removing the override made the three widget tests fail; web build OK.
Not verified: the fix on a real keyboard (the emulator hung on restart). The owner's phone check after deploy.
