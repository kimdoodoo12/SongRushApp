# SongRushApp 자율 개발 체계

이 문서는 SongRushApp(애니 OP/ED 멀티플레이 맞히기 웹사이트)을 만드는 **바이브 코딩 과정 자체**의 기록입니다(포트폴리오 자료). 에이전트 운영 규칙은 `CLAUDE.md`와 `.claude/skills/vibe-cycle/SKILL.md`에 있고, 여기에는 설계 이유와 실제로 일어난 일을 근거(커밋 SHA, 명령 출력)와 함께 남깁니다.

기술 스택(D-029, D-030): 게임 서버는 Java Spring Boot(JDK 17, `backend/`), 웹 화면은 React(순수 JavaScript, TypeScript 없음, `frontend/`), 데이터 처리는 Python 3.12(`data/`)입니다. 구조 설계는 새 조사(S-001~S-003)로 다시 세웁니다.

## 1. 풀려는 문제

- **사람은 감독만 하고 싶다.** 매 단계 승인 없이 에이전트가 계속 개발하고, 사람은 방향(Roadmap)과 결정 사항만 다룹니다.
- **멀티플레이 게임은 "돌아가는 것 같다"로는 부족하다.** 한 플레이어만 음원을 먼저 듣거나 정답이 클라이언트로 새면 게임이 성립하지 않습니다. 그래서 공정성과 정답 보호를 리뷰의 고정 항목으로 둡니다.
- **음원은 외부 자원이다.** Python 도구가 AnimeThemes에서 음원을 받아 AAC로 캐시하고(인기 상위 약 1,500곡은 미리), 아직 없는 곡은 Spring Boot 서버가 로비 대기 중에 받습니다. 라운드마다 추측할 수 없는 주소로 곡 전체(최대 90초)를 보냅니다. 테스트가 외부 서버 상태에 흔들리지 않도록, 테스트는 저장해 둔 응답(fixture)만 씁니다.
- **같은 규칙이 두 언어에 있을 수 있다.** 채팅 정답 비교용 정규화를 Python(데이터)과 Java(게임 서버)가 함께 쓰게 되면, 두 구현이 어긋나는 순간 정답이 조용히 오답 처리됩니다. 그런 약속은 공유 테스트 벡터(`contracts/`)로 JUnit과 pytest가 함께 확인하게 하고, Stop hook은 `contracts/`가 바뀌면 두 영역을 모두 돌립니다.
- **할 일을 사람이 티켓 단위로 계속 써 줄 수 없다.** 큰 목표만 주면 에이전트가 스스로 작업을 쪼개 이어 가야 합니다.

## 2. 설계 원칙

1. **증거만 인정한다.** "됐다"는 말이 아니라 verifier가 실제로 실행한 명령 출력만 통과로 칩니다.
2. **만든 사람이 검증하지 않는다.** 코드는 implementer가 쓰고, 실행은 verifier, 반론은 critic이 합니다.
3. **테스트를 먼저 쓰고 잠근다.** 구현자가 테스트를 고쳐서 통과시키는 것을 hook으로 막습니다.
4. **안전은 질문이 아니라 장치로 강제한다.** 권한 목록, hook, git 브랜치로 막습니다. 제품 결정은 사람이 대화 중이면 바로 묻되, 답을 기다리며 작업을 멈추지는 않습니다(D-028, 2026-11-02 사용자 지시). 사람이 없으면 "Needs decision"에 쌓습니다.
5. **범위는 사람이 정한다.** 에이전트는 Roadmap에 적힌 것만 쪼개고, 리뷰 지적 사항(Follow-ups)은 스스로 작업 큐에 올리지 않습니다.
6. **기술 스택은 사람이 정한다.** 이전 시도에서 에이전트가 스택을 묻지 않고 정했다가 전부 다시 시작하게 됐습니다(D-031). 스택처럼 되돌리기 비싼 선택은 제품 방향 결정으로 보고 사용자에게 묻습니다.

## 4. 사이클의 종류와 흐름

**구현 사이클** (`B-` 게임 서버, `F-` 웹 화면, `C-` 카탈로그·음원 데이터, `I-` 인프라)
1. 명세 작성 → critic이 명세 검토 (최대 2회)
2. implementer가 테스트 작성 → verifier가 "올바른 이유로 실패"하는지 확인 → 커밋 후 잠금
3. implementer가 구현 (최대 3회 시도)
4. verifier가 테스트·lint 실행, 잠긴 테스트가 바뀌지 않았는지 `git diff`로 확인
5. critic이 diff 검토: 범위, 버그, 음원 규칙, 정답 유출, 서버 기준 타이밍
6. `dev`로 PR을 열고 GitHub CI 통과를 기다림 (실패하면 3단계로 돌아가 시도 횟수 증가)
7. dev에 병합, `PROGRESS.md`에 한국어로 기록

**설계 사이클** (`S-`): 조사 → 설계 문서(근거, 선택지, 결정) → critic 검토 → 결과 작업을 Ready 끝에 추가. 새 스택의 조사와 설계(S-001~S-003)가 여기에 해당합니다.

**계획 사이클** (Ready가 비었을 때): Roadmap의 다음 마일스톤을 3~8개 작업으로 쪼개 Ready에 넣습니다. critic이 "마일스톤에 없는 것"과 "한 사이클에 안 끝날 크기"를 검사합니다. 이 사이클 덕분에 `/loop /vibe-cycle`이 사람의 티켓 입력 없이 계속 이어집니다.

Roadmap: M-1 혼자 플레이 프로토타입 → M-2 방 → M-3 동기화 라운드와 점수 → M-4 배포 → M-5 애니 특화 모드

## 5. 역할 분리

| 에이전트 | 할 수 있는 것 | 할 수 없는 것 |
|---|---|---|
| lead (메인 세션) | 명세, 위임, 병합, 기록 | 제품 코드·테스트 작성 |
| explorer | 코드·외부 자료 조사 | 파일 수정 |
| implementer | 배정된 파일만 수정 | 배정 밖 파일, 잠긴 테스트 수정 |
| verifier | 명령 실행과 결과 보고 | 코드 수정 |
| critic | 반론과 결함 지적 (확신 80 이상만) | 파일 수정 |

## 6. 강제 계층

### 6.1 권한 (`settings.json`)
- 허용: git 조회·커밋·브랜치, dev와 cycle 브랜치 push, 영역별 빌드·테스트 명령(`gradlew`, `npm`, `pytest`), AnimeThemes와 GitHub 조회
- 확인 필요: `settings.json`과 hook 파일 수정 (에이전트가 자기 감시 장치를 고치지 못하게)
- 금지: 강제 푸시, main push, `reset --hard`, `rm -rf`, `.env` 읽기

### 6.2 hook
| hook | 시점 | 하는 일 |
|---|---|---|
| `guard.py` | 도구 실행 전 | 잠긴 테스트 쓰기, main 커밋, 강제 푸시, main push, 히스토리 재작성 차단 |
| `lock.py` | lead가 직접 실행 | 테스트 경로 잠금·해제 |
| `check_on_stop.py` | 종료 시 | 바뀐 영역의 테스트 실행: `backend/`는 `gradlew test`, `frontend/`는 `npm test`, `data/`는 `pytest`. `contracts/`가 바뀌면 `backend/`와 `data/`를 둘 다 돌림. 테스트가 잠긴 구현 단계에서 실패하면 종료를 막고, 3회 넘게 실패하면 `blocked.log`에 기록. 준비 안 된 영역은 UNVERIFIED로 알리고 통과로 치지 않음 |
| `notify_discord.py` | 종료 시 | 네 가지 모드로 Discord에 알림. `stop`(프로젝트): `PROGRESS.md`의 새 결정 요청이나 새 BLOCKED. `notification`(전역): 권한 확인 창이나 입력 대기. `failure`(전역): 사용량 한도·과부하·네트워크 같은 API 오류로 턴이 끝났을 때. `end`(전역): 세션 종료. 네트워크가 끊겨 보내지 못한 알림은 outbox에 쌓아 두고, 백그라운드 재전송기가 다시 보냄. 항상 종료 코드 0이라 알림 실패가 사이클을 막지 않음 |

### 6.3 브랜치
- `main`: 배포용. 사용자만 병합합니다.
- `dev`: 통합용. verifier와 critic을 통과한 사이클만 병합합니다.
- `cycle/NNN-slug`: 사이클마다 하나씩, dev에서 만듭니다.

### 6.4 프로젝트 고유 규칙
- 음원·영상 파일은 저장소 용량 때문에 커밋하지 않습니다. 음원 캐시와 HTTP 캐시는 `data/cache/`(gitignore)에 두고, 개발 PC에서 만들어 서버 디스크로 옮깁니다. 저장소에는 `data/catalog.json` 같은 메타데이터만 둡니다.
- 외부 요청은 설계 사이클, 카탈로그 빌드, 음원 캐시 빌더(Python), 게임 서버의 로비 대기열(Java)에서만 합니다. 테스트는 저장된 fixture만 씁니다.
- Python 도구와 Java 서버 사이의 약속(파일 형식, 이름 규칙, 잠금, 정규화)은 설계 문서에 고정하고, 약속마다 양쪽 테스트를 둡니다.
- 제품 결정(사용자, 2026-11-02, 최신):
  - 애니 제목을 채팅으로 맞히고, 서버에 먼저 도착한 정답 1명만 1점을 받습니다.
  - 곡 전체를 처음부터 최대 90초까지 들려줍니다.
  - 스킵은 과반 투표로 하고, 라운드 수는 방장이 정합니다.
  - 음원은 서버가 받아 opaque 주소로 전달하고, 출제는 인기 상위 1,500곡에서 합니다.
  - 처음 결정(D-002 직접 재생, D-004 고정 클립)은 조사 결과에 따라 D-009·D-018로 대체되었습니다.
- 서버가 정답, 라운드 시계, 점수를 관리합니다. 한 클라이언트만 먼저 듣는 공정성 버그는 High 등급입니다. 서버 도착 순서는 동시에 들어온 메시지에서도 서버가 직접 보장합니다(D-016).

### 6.5 사용자가 정한 진행 방식 (2026-11-02)
- **`PROGRESS.md`는 소유자의 진행 보고서입니다.** AI용 메모가 아니라, 개발자가 아닌 사람이 읽는 한국어 보고서로 씁니다. 커밋 SHA, 등급 표시, 에이전트 이름, 시도·테스트 횟수는 넣지 않고, 항목마다 "기록:" 한 줄로만 상세 문서를 가리킵니다.
- **"다음 진행 예정"은 매번 새로 씁니다.** 이전 계획은 지우고 남기지 않습니다.
- **멈추지 않고 이어 갑니다.** 결정이 필요해도 답을 기다리며 멈추지 않고, 질문을 "Needs decision"에 올린 뒤 다음 작업으로 넘어갑니다(D-028).
- **사람이 필요할 때만 Discord로 알립니다.** 입력 대기, 결정 요청, BLOCKED, API 오류, 세션 종료입니다. 턴이 끝날 때마다 보내던 알림(`halt`)은 사이클 중 에이전트를 기다릴 때도 울려서 2026-11-03에 사용자 요청으로 껐습니다.

## 7. 구축 과정에서 실제로 일어난 일

아래 두 일은 이전 Node/TypeScript 시도에서 개발 체계를 세울 때 있었습니다. 그 시도의 git 히스토리는 남아 있지 않지만, hook과 규칙은 이 저장소로 그대로 옮겨 왔으므로 교훈도 함께 남깁니다.

### 7.1 hook을 먼저 시험했습니다
첫 사이클 전에 시험 스크립트로 hook에 가짜 입력 8개를 넣었고, 모두 기대한 종료 코드가 나왔습니다.
- 차단(종료 코드 2): main 커밋, 강제 푸시, main push, 잠긴 테스트 쓰기
- 통과(종료 코드 0): `git status`, 소스 파일 쓰기, 준비 전 Stop hook, Discord 알림

### 7.2 세팅 중 hook이 두 번 막았습니다
- **시험 명령이 차단됨.** 시험용 셸 명령 안에 강제 푸시 문자열이 들어 있었습니다. 가드는 명령 문자열 전체를 정규식으로 검사하므로 실행 전에 막았습니다. 시험 입력을 스크립트 파일로 옮겨 해결했습니다.
- **`git switch -c dev && git commit`이 차단됨.** 가드는 명령이 *실행되기 전*의 브랜치(main)를 기준으로 판단하므로, 같은 줄에서 브랜치를 바꿔도 통하지 않습니다. 전환과 커밋을 두 명령으로 나눠 해결했습니다.

두 사례 모두 `CLAUDE.md`의 "Pitfalls learned"에 한 줄씩 남아 있습니다.

- 사이클 019: lead가 테스트 잠금 상태 파일을 직접 읽으려 하자 `guard.py`가 막았습니다("only the lead uses lock.py"). 같은 사이클에서 lead가 잠긴 테스트가 아직 실패하는 동안 턴을 두 번 끝냈고, Stop hook이 이를 실패 시도 2/3으로 셌습니다. 이후 lead는 테스트가 통과할 때까지 턴 안에서 기다렸습니다(`docs/cycles/019-korean-titles.md`).

### 10.4 critic이 잡아낸 문제
명세 검토와 코드 검토에서 critic이 Blocker·High로 올린 것 중 대표적인 것입니다. 근거는 각 사이클 문서의 "Review changes"와 "Code review" 절입니다.
- 012 서버 기본 틀: Spring Boot 4에서 `TestRestTemplate`이 옮겨져, 기억에 의존해 쓴 테스트는 컴파일조차 되지 않았을 것입니다. 또 Stop hook 상한(900 s)이 백엔드 테스트 시간 제한(1500 s)을 잘라 먹고 있었습니다.
- 013 데이터 환경: 테스트 중 네트워크를 막는 장치가 `connect`만 막아서, DNS 조회(`getaddrinfo`)가 실제로 밖으로 나가고 있었습니다.
- 015 정답 비교: 최소 길이 4자 규칙이 `나루토`, `銀魂` 같은 짧은 CJK 제목을 막는 문제(Blocker)를 잡았습니다. Python의 `casefold()`가 Java에서 83개 코드포인트에서 다르게 동작한다는 점도 찾았습니다. 코드 검토에서는 일부러 넣은 버그 12개 중 11개가 테스트를 통과한다는 것을 보여, 테스트를 보강하는 2차 시도로 이어졌습니다.
- 016 요청 도구: urllib의 `HTTPError`가 `OSError`의 하위 클래스라서, 404가 재시도 대상으로 잘못 분류되고 `Retry-After`를 잃을 수 있었습니다. 코드 검토에서는 상한을 넘는 대기 뒤 다음 요청이 로그 없이 86400 s 동안 잠드는 문제를 재현했습니다(2차 시도).
- 017 AnimeThemes 수집: 요청과 다른 페이지가 응답으로 오면 그대로 영구 캐시되어 중복 오류가 끝없이 반복될 수 있었습니다.
- 019 한국어 제목: 받아 둔 aod 파일이 한 번 깨지면 이후 모든 수집이 한국어 제목 약 2,661개 없이 진행된다는 점(High)을 잡아, 원본 크기와 해시를 고정하게 했습니다. 코드 검토에서는 자모가 분리된(NFD) 한국어 제목이 빠진다는 점을 실제 파일로 재현했습니다.
- 062 DuckDNS·무료 플랜: 명세 검토에서 critic이 UUID 금지 검사가 `smoke.py`의 RFC 6455 GUID 때문에 반드시 실패한다는 점(Blocker)과, '잘못된 이름' 사례가 기존 hostname 정규식에 먼저 걸려 아무것도 검증하지 않는다는 점(High)을 직접 실행해 보였습니다. DuckDNS 단계를 apt 앞의 별도 스크립트로 떼어 테스트 훅을 두 경로로 줄였습니다. 코드 검토는 토큰이 질문 전에 붙여 넣어지면 셸 기록에 남는 경로(Medium)를 찾았고, 사장님이 곧 따라 할 안내서라 병합 전에 고쳤습니다(`08bae82`).
- 061 출제 조건(화면): 명세 검토에서 critic이 서버가 `settings`를 첫 `prepare`보다 먼저 보내므로 'prepare에서 줄 지우기' 규칙이면 줄이 받자마자 사라진다는 점(Blocker)을 코드 순서로 보였습니다. 또 lead가 잠금 패턴을 glob으로 걸어 새 테스트 파일까지 잠갔는데, 테스트 작성자가 guard에 막힌 것을 우회하지 않고 보고해 파일 이름 목록으로 다시 잠갔습니다.
- 060 출제 조건(서버): 명세 검토에서 critic이 `*.ogg`가 gitignore라 정적 테스트 음원이 새 clone에서 사라져 후보가 0개가 된다는 점(High)과, 늦게 들어온 사람·재접속·소켓 교체마다 조건 안내 위치가 다르게 적혀 있다는 점(High)을 짚어 `@TempDir` 생성과 snapshot 직후 한 곳으로 고쳤습니다. 테스트 커밋부터 backend 테스트 전체를 잠갔습니다.
- 059 M-5 계획: critic이 계획의 '오류에 남은 곡 수 추가'가 잠긴 `RoomTest`의 오류 키 집합 고정과 충돌한다는 점(High)과, 조건을 방장만 알면 그 자체가 힌트가 된다는 점(Medium)을 짚어 선언된 변경과 `settings` 메시지로 계획을 고쳤습니다. 실제 캐시 곡을 연도별로 세어 1990~94년이 0곡임을 보이고 5년 단위 선택지로 바꾸게 했습니다.
- 058 배포 안내서: 명세 검토에서 critic이 Git Bash에서 `.\gradlew.bat`의 백슬래시가 사라지고 `chmod 600`이 NTFS(`noacl`)에서 아무 효과가 없음을 실제로 실행해 보였습니다(High). 코드 검토에서는 재시작 절의 한 명령 상자에 내 PC용 `ssh`와 서버용 `setup.sh`/`exit`가 섞여 있어 통째로 붙여 넣으면 엉뚱한 곳에서 실행된다는 점(High)을 잡아 2차 시도에서 나눴습니다. 같은 사이클에서 Stop hook이 `docs/` 변경에도 data 테스트를 돌리도록 넓혔습니다(커밋 `9a33364`).
- 057 설치 도구 다듬기: 명세 검토에서 critic이 잠긴 055 테스트가 한 로그 줄에서 `mv`와 `restart`를 찾고 dry-run 출력 전체에서 ` -r`을 금지한다는 점을 들어, 새 원격 명령을 줄바꿈 없는 작은따옴표 한 줄로 못박게 했습니다(High). 또 '이전 jar'를 재시도가 덮어쓰는 경로(Medium)를 보여 '마지막 정상 jar'(`.good`)로 바꿨습니다. verifier는 그 원격 명령을 스텁 `sudo`/`curl`로 실제 실행해 확인했습니다.
- 056 접속 확인 도구: 명세 검토에서 critic이 `git ls-files --eol`로 cycle 055의 `deploy/` 파일이 checkout 뒤 CRLF가 되어 dev에서 이미 테스트가 실패하고 있음(Blocker)을 보였습니다. 055의 verifier는 commit 전 LF 파일을 검사해 통과했던 것입니다. `.gitattributes`에 `deploy/** text eol=lf`를 넣고 CLAUDE.md 함정에 기록했습니다(커밋 `45b9813`). verifier는 실제 jar에 대고 스크립트를 돌려 4개 OK를 확인했습니다.
- 055 배포 도구: 명세 검토에서 critic이 Git Bash에 든 `sftp-server.exe`에 `sftp -b`를 붙여 실제로 돌려 보고, `reput`/`put -r`/`mkdir`가 두 번째 배포부터 멈추거나 폴더를 겹친다는 점(Blocker)과 PowerShell에서는 `bash`가 WSL 실행기로 잡힌다는 점(High)을 보였습니다. lead의 명세 수정 스크립트가 escape 오류로 실패해 테스트 작성자가 옛 명세로 시작했다가, 잠그기 전에 다시 맞췄습니다. 같은 날 Stop hook이 `deploy/` 변경에 data 테스트를 돌리도록 `EXTRA_AREAS`를 넓혔습니다(커밋 `14741b6`).
- 054 프록시·정적 화면: 명세 검토에서 critic이 Gradle 캐시의 Boot·Tomcat 소스를 읽고, 시작 가드가 한 방향만 막아 데이터 폴더를 품는 정적 폴더가 `catalog.json`과 음원 이름을 내보낸다는 점(High)과, JDK HttpClient가 `Host` 헤더를 금지해 테스트를 쓸 수 없다는 점(jshell로 확인)을 잡았습니다. 테스트 작성자는 spring-websocket이 사용자 `Host` 헤더를 버린다는 점을 찾아 테스트 전용 하위 클래스로 우회했습니다. verifier는 실제 jar로 101/403과 가드 실패를 확인했습니다.
- 053 AWS 무료 조건(설계): explorer가 공식 문서로 "12개월 무료" 가정(D-065)이 2025-07-15 이후 신규 계정에는 맞지 않음을 확인했고, critic은 같은 페이지의 표를 curl로 받아 '가입 시 유료 플랜'이라는 선택지가 빠졌다는 점(High)을 지적했습니다. 비용 선택은 D-068로 사장님 결정에 남겼습니다.

- 051 늦은 시작 신호 보정: 명세 검토 1차에서 critic이 처음 설계(새 추정값의 중앙값으로 보정)가 비대칭 경로나 시계 점프 직전 ping의 pong 때문에 곡을 최대 약 750 ms 먼저 틀 수 있음(High)을 계산으로 보였고, 보정값을 표본별 하한 `serverTime - t1`로 바꿨습니다. 2차에서는 바 검사가 상한에 막혀 아무것도 구분하지 못한다는 점(Blocker)과, '대기 중 ping 버리기'의 진짜 위험은 다음 곡의 추정값이라는 점(High)을 잡아 테스트 사례를 고쳤습니다(커밋 `7de9a4d`, `1433d50`). 구현은 1차 시도에 통과했습니다(`0549fc7`).

- 049 자동 재접속: 명세 검토에서 critic이 백엔드 코드로 "재접속 소켓이 joined보다 먼저 밀린 방송을 받는다"는 점을 보여 곡이 이중 재생될 수 있는 경로(High)와, 연결 중인 소켓에 `leave`를 보내면 브라우저가 예외를 던져 화면이 멈추는 경로(High)를 잡았습니다. verifier는 실제 서버에서 소켓을 끊고 다시 붙여 프로토콜을 확인했습니다. 이로써 M-3이 완성됐습니다.

### 10.5 절차 변경
- 사이클별 PR (D-093, 설계 078): 이전에는 사이클을 로컬에서 `dev`에 병합한 뒤 push했기 때문에 GitHub CI가 병합 후에야 돌았고, 그 결과를 읽는 단계도 없었습니다. 이제 사이클마다 `dev`로 PR을 열고 CI 통과를 기다린 뒤 병합합니다. 에이전트는 `gh pr merge`를 쓰지 않고 로컬 병합 후 push해서 PR을 닫으므로, `dev → main` 병합 권한은 계속 사람에게만 있습니다.
